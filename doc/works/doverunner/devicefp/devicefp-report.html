Verdict

No OS-version-attributable defect remains

Three code defects surfaced during this campaign. Two were specific to a platform version and one to a vendor; all three are fixed and re-verified on the handsets that exhibited them. Every remaining advisory across the fleet is a correct reading of a real device condition: six handsets have unlocked bootloaders and say so, and one handset is misrepresenting its hardware and is now flagged for it.

The figures throughout describe logic 13, run r21 — the last round before the library was split out for packaging. That split is covered further down, along with the one thing it left open.

Collectors behave consistently across versions. All eight report on every handset, and the missing-signal set is the same families at every API level — no SIM inserted, no proxy configured, no GSF id — rather than anything version-specific. Fingerprints are stable both within a run and across app restarts.

Fixed

Defects found and closed

Defect 2 · native · api29 arm64

Reading a libc prologue killed the whole collection

The inline-hook probe dereferenced a libc code pointer directly to inspect the function prologue. Android 10 maps AArch64 platform libraries execute-only, so the read faults. The process died after gathering everything and before sending, which is why it surfaced as silence rather than as a failing check: the client re-registered a few seconds after taking a collect and delivered nothing.

Execute-only was withdrawn by api34 and never applied to armeabi-v7a, which is why only three handsets were affected. Fixed by reading the instruction bytes through /proc/self/mem, which the kernel performs on the caller's behalf and is not bound by the mapping's read bit — so the probe keeps working on execute-only devices instead of being skipped there.

Defect 5 · native · api29–api30

ART's own JIT cache was reported as a tamper indicator

Healthy handsets with locked bootloaders raised anonymous_executable_region and deleted_executable_mapping, cutting confidence to 0.48. Not a heuristic problem but a naming mismatch in the exclusion list: the api29 path is /memfd:/jit-cache, with a second slash the "/memfd:jit" test could not match, and the affected api30 handset names its ashmem region jit-zygote-cache rather than dalvik-*.

One such line raises both bits at once, satisfying the (deleted) test and the memfd: test together, which accounts for every number in the observed distribution. After the fix the rate is 0/34 at every API level, and the other 30 handsets did not change by a single bit — the exclusion was tightened onto the real names, not widened.

Defect 3 · Kotlin · vendor-specific

An impossible panel DPI was accepted as a measurement

One handset reports display.physical_dpi = 3976x3958 where the other 33 land between 260 and 452; a second reports 72x72. The value comes from panel metadata this vendor populates wrongly, and the collector passed it through verbatim at IMMUTABLE weight 0.7.

Being wrong but constant, it satisfied every stability check — precisely the failure mode the codebase already refuses elsewhere, where a bucket that cannot be determined is left absent rather than published. The signal is now absent outside 100–1200 dpi. Exactly two handsets changed; no legitimate value was dropped.

Found

One handset is not the hardware it claims to be

SM-S908E presents a coherent Galaxy S22 Ultra identity — board taro, a Snapdragon 8 Gen 1 — over hardware that is nothing like one: Adreno 650 rather than 730, four cores rather than eight, 3 GB rather than 8–12, a 720×1280 panel rather than 1440×3088, and software-only key attestation. The Build fields and the property store agree with each other throughout, so the existing layer-comparison check reported no mismatch.

Two structural rules were added in response. Rather than asking whether the layers agree, they ask whether the answer is possible at all: a bootloader that published a verified-boot state also published a lock state, and a platform claiming api31 or above has the ro.soc.model property that Android 12 mandates. Both were validated against all 34 handsets before being written.

Fires on one handset and none of the other 33, including all six with unlocked bootloaders — those publish a lock state, so the rule correctly stays quiet. Both rules are defeated by a spoofer who adds the two missing properties: they catch incomplete synthesis, and do not replace the attestation signal, which is the only anchor rooted in a key the device does not hold.

Inventory

What the suite collects

Every value is hashed on the device; the report carries digests, never the raw string, except for a comparable subset the harness keeps in the clear so two runs can be diffed. A signal that cannot be read is reported as absent rather than dropped — absence is itself weakly identifying, and it keeps a blocked path from reading as a clean result.

Weight is the contribution to a fingerprint match, 0.1 to 1.0. “Read by” is the layer that reaches the value: native goes to /proc, /sys, statvfs and the property store through raw syscalls; framework goes through binder services.

Four vectors, by how long each survives

Signals carry a stability class, and the vectors are cumulative slices of it. This is what lets a backend choose recall over precision or the reverse, per decision.

VectorContentsSurvivesBreaks on
v0IMMUTABLE only factory reset, OS upgrade hardware change
v1+ STABLE reinstall, data wipe OS upgrade, vendor OTA
v2+ VOLATILE nothing much — highest entropy user setting changes
v3ANCHOR only used as an exact-match join key identifier reset

The gating checks in this report are built on v0–v2: repeat_stable requires them identical across two collections in one run, and baseline requires them identical to a vector stored on an earlier launch.

Integrity evidence, kept out of identity

Twenty-three further signals carry tamper and attestation evidence at weight 0.0, so they never enter a vector: key attestation chain and security level, verified-boot and bootloader lock state, ro.debuggable and ro.secure, adb and developer-settings state, accessibility services, the native tamper bitmask, and the cross-layer checks. Keeping them at zero weight is what allowed the checks added during this campaign to ship without invalidating a single stored baseline.

Deliberately not collected

No IMEI, MEID, serial number or MAC address, and no property that carries one. Those are restricted identifiers under Google Play's user-data policy and are unreadable to a third-party app from api29 anyway; collecting them would create a compliance liability for no signal. The one exception in spirit is a reboot-scoped boot-id hash, which is a nonce rather than an identifier and exists to tell a genuine reboot apart from a snapshot-restored emulator replaying a session.

Integrate

Using it from another app

The library is packaged as an AAR carrying the collectors, the canonicaliser, the vectors, the integrity verdict and libdevicefp.so for all four ABIs. The harness wrapper — the plugin entry point and the on-device screen — is a separate module and is not part of it. Nothing in the library knows a harness exists.

  1. Depend on it

    No permissions are declared and no manifest entries are needed. ProGuard rules travel inside the AAR, so a shrinking build keeps the JNI binding and the public types without you adding anything. Minimum minSdk 26.

    // build.gradle.kts
implementation("com.doverunner.appsealing:devicefp:1.0.0")

  2. Collect

    One call, off the main thread. The native core loads itself on first use, so there is nothing to initialise and no lifecycle to manage.

    // Kotlin — @WorkerThread
val report = DeviceFingerprint.collect(context)

report.vector(Vector.V0_SILICON)   // hardware-bound, survives factory reset
report.vector(Vector.V1_PLATFORM)  // the primary vector
report.integrity.confidence        // 0.0–1.0 multiplier
report.integrity.reasons           // e.g. [attestation_software_only]
report.toJson()                    // digests only; pass true for raw values
    // Java — @JvmStatic and @JvmOverloads are already on the entry points
FingerprintReport report = DeviceFingerprint.collect(context);
String v1 = report.vector(Vector.V1_PLATFORM);

    With no worker pool of your own, collectAsync(context, callback) runs it on a single-use executor and hands the report back.

  3. Pass a server nonce for attestation

    The one setting that matters for security. Without a server-issued challenge the attestation chain is replayable: an attacker captures a chain from a clean device and presents it from a rooted one. Attestation is the only signal in the report rooted in a key the device does not hold, which is what makes it worth having — it is the signal that caught the spoofed handset above.

    val report = DeviceFingerprint.collect(
    context,
    DeviceFingerprint.Config(
        attestationChallenge = nonceFromYourServer,  // always, in production
        enableGpu = true,          // offscreen GL probe, ~100–400 ms
        enableDrmId = true,        // Widevine id, strongest resettable anchor
        enableGsfId = false,       // needs READ_GSERVICES in YOUR manifest
        globalTimeoutMs = 3_000L,  // hard ceiling on the whole collection
    ),
)

  4. Judge on the server, not on the device

    Send the report and decide there. Everything a device says about itself can be rewritten by whoever controls it; what a backend can do that a client cannot is compare this report against other reports. Treat confidence as a weight on how much a fingerprint match counts, never as a block-or-allow verdict — a rooted developer handset is not a fraudster, while a rooted handset whose v0 matches eleven other accounts is.

Integrate

Using the native core on its own

The same libdevicefp.so exposes a plain-C surface with no JNI and no JVM requirement, for an NDK app or another native library that wants the kernel-sourced signals without going through Kotlin. This is the surface the harness uses, which is why it exists: the harness opens the library with dlopen so it can close it again, and a caller with no JVM at all can use exactly the same four functions.

Know what you give up. Canonicalisation, the v0–v3 vectors and the integrity verdict all live in the Kotlin layer. The native surface hands back raw key/value pairs and a bitmask; it does not compute a fingerprint. Everything framework-sourced — sensors, cameras, codecs, GL strings, DRM, Settings, key attestation — is not in this surface at all.

// Four exported symbols. Everything else is hidden (-fvisibility=hidden).
const char *df_collect(const char *);       // key  value  key  value …
int         df_tamper_flags(const char *);  // DF_TAMPER_* bitmask
const char *df_sha256(const char *);        // 64 hex chars, or null
void        harness_native_free(const char *);

// Optional. Hands over the process JavaVM so the library can read the few
// framework values it reads through JNI. Skip it and those are simply absent.
void        harness_native_set_vm(void *javaVM);
// dlopen, call, free. Every text return is owned by the caller.
void *h = dlopen("libdevicefp.so", RTLD_NOW | RTLD_LOCAL);
auto collect = (const char *(*)(const char *))     dlsym(h, "df_collect");
auto release = (void (*)(const char *))            dlsym(h, "harness_native_free");
auto flags   = (int (*)(const char *))             dlsym(h, "df_tamper_flags");

const char *flat = collect(nullptr);
// Split on : even fields are keys, odd fields are values.
int tamper = flags(nullptr);
release(flat);          // required — the library allocated it
dlclose(h);

Linking it directly instead of dlopen works too and is simpler; dlopen is only needed if you want to be able to close it again. harness_native_free is not optional: the library allocates with its own statically linked libc++, so it has to be the one that frees.

The framework values the native side does read — android.os.Build through JNI — need a JavaVM. Hand one over with harness_native_set_vm, or on api31 and above the library finds it itself through libnativehelper.so. Below api31 there is no self-service route, so without the handover those values are absent.

Verified

What the rounds establish

Stability across app restarts

Each logic push restarts the client, so rounds r20 and r21 compared every handset's vectors against a baseline stored before that restart. All 34 matched, twice. Within a run, the two collections of every handset were identical.

No version-specific collector gap

All eight collectors reported on all 34 handsets, and api29 collects one signal more than api34. Absences track device configuration — SIM, proxy, accessibility services — not platform version.

Both shipping ABIs exercised

arm64-v8a on 32 handsets and armeabi-v7a on two, including the 32-bit branch of the new per-ABI syscall code.

Open

Limits of this report

x86 and x86_64 were compiled but never run

No such handset is in the fleet, so the x86 branch of the new pread wrapper is compile-verified only.

The coherence rules rest on a single positive case

One spoofed handset. Both rules are structural rather than fitted to it, and both are trivially defeated by adding the two properties they check for.

Two dual-read stages detect nothing

Reading Build.* a second time through JNI resolves the same static fields, so it is one reading rather than two. Reading panel geometry from sysfs is genuinely independent but blocked by SELinux on 33 of 34 handsets. Both are correct code that earns nothing; whether to remove them is a decision still to take.

One handset went intermittently unstable after the library split

Splitting the collection logic into a publishable module changed no collection code — the files were moved, and every handset still matches the fingerprint it stored before the split, which is the check that matters for packaging. But SM-G960N has since failed repeat_stable in two rounds of three, where it passed four for four before.

What is ruled out: no collector was dropped (all eight report), the signal set and the absent set are identical between passing and failing rounds, and at 310/313 ms against a 3000 ms budget there is no deadline pressure — the slowest handset in the fleet takes 1887 ms and passes. The first collection is always correct; the second drifts. So a present signal is changing value between two back-to-back reads on this one device.

Whether the split caused it or surfaced existing flakiness is not yet established, and four passing rounds against two failing is too little to call. Pinning it needs the check to report which comparable key moved; today it reports only that one did, which is the same gap that made the layer-agreement signal hard to action until it was given values to show.

Harness tooling issues, outside the suite

A runtime push is consumed but never applied, leaving clients on the seeded runtime. The deploy script grants a notification permission before launching, which fails below api33 and takes the launch with it. A suite's native library is not carried in the APK seed, so a freshly installed handset needs an explicit push before its numbers mean anything.
